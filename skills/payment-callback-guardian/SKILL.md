# 支付回调守卫

支付回调来自外部网络，而且会重试、乱序、重复甚至被伪造。把它当成一条需要验证、去重和恢复的资金状态输入，而不是普通 HTTP POST。

## 边界

本 Skill 处理支付与退款异步通知的代码、设计和故障调查。支付页面视觉、商品定价、商户开户注册和法律意见不在范围内。

优先读取仓库当前实现和渠道官方文档。渠道、接口版本、签名算法或证书体系不明确时，不要凭记忆补齐。

需要核对微信支付或支付宝当前契约时，读取 [`references/official-contracts.md`](references/official-contracts.md)，并只选择项目实际使用的渠道与版本。

## 工作流

### 1. 锁定渠道契约

记录：

- 渠道与 API 版本；
- 支付、退款或撤销通知类型；
- 请求方法、头部、原始报文和响应要求；
- 商户号、应用号、平台证书序列号等身份字段；
- 官方文档版本或链接；
- 当前订单状态机和唯一键。

不要混用不同版本的验签或证书规则。

### 2. 保留原始报文

验签通常依赖未经重新序列化的原始字节、时间戳、随机串、签名和证书标识。检查 Web 框架是否在验签前已经解析、改变编码或重排 JSON。

原始报文可以短暂参与验签，但日志中不要完整记录姓名、手机号、证件号、支付凭证或密文材料。

### 3. 先验证来源，再相信业务字段

按渠道当前官方规则验证签名、证书有效性和必要的时间窗口。签名失败、证书未知或解密失败时：

- 不更新订单；
- 不触发发货、积分或通知；
- 返回渠道规定的失败响应或进入安全重试；
- 记录可关联但不泄密的诊断信息。

不要用来源 IP 白名单替代签名验证。

### 4. 交叉核对订单事实

通过可信的商户订单号找到本地订单，并核对：

- 商户号与应用号；
- 本地订单号和渠道交易号；
- 金额、币种和最小货币单位；
- 通知类型和支付状态；
- 商品或业务主体标识；
- 已知的退款、关闭和撤销状态。

金额或身份不一致时应隔离调查，不能因为渠道状态写着 SUCCESS 就更新订单。

### 5. 设计单向状态机

明确允许的状态转移，例如 `PENDING -> PAID`。终态不能被迟到通知倒退，支付成功通知也不能覆盖已确认的全额退款。

把状态判断和写入放在同一事务或等价的原子条件更新中。以渠道交易号、通知 ID 或业务幂等键建立唯一约束，而不是只在内存里判断“处理过”。

### 6. 隔离一次性副作用

发货、发券、记账、积分和消息通知只能在资金状态成功提交后触发一次。优先使用事务消息、Outbox 或可重放任务，让数据库提交成功但下游暂时失败时可以恢复。

不要在数据库提交前向渠道返回成功；也不要因为下游短信失败而重复改变订单资金状态。

### 7. 处理重复、并发和乱序

至少验证：

- 完全相同的通知连续到达；
- 两个实例并发处理同一通知；
- 成功通知晚于关闭或退款通知；
- 首次处理在提交前、提交后或副作用中途崩溃；
- 渠道超时重试；
- 手工补单与回调同时发生。

对重复成功通知返回渠道期望的成功响应，但不重复发放权益。

### 8. 建立主动查询与对账闭环

回调不是唯一事实来源。为长时间 PENDING、回调缺失、金额冲突和退款异常设计主动查询或账单对账。记录差异、负责人和补偿动作，不要自动“猜测修复”资金数据。

### 9. 形成验证矩阵

覆盖有效通知、篡改报文、错误证书、金额不一致、未知订单、重复、并发、乱序、数据库失败、下游失败和渠道重试。测试应证明最终状态和副作用次数，而不只是 HTTP 200。

## 停止条件

遇到以下情况停止并请求信息或批准：

- 无法确定渠道或 API 版本；
- 需要真实商户私钥、API 密钥或生产证书才能继续；
- 本地订单状态机或金额单位未知；
- 修复需要直接修改生产资金数据；
- 官方契约与仓库实现明显冲突但无法确认迁移计划。

## 输出约定

1. **结论**：通过、修改后通过、阻断或信息不足。
2. **回调信任链**：原始报文、验签、解密和身份核对顺序。
3. **状态机与幂等设计**：唯一键、原子边界和允许转移。
4. **资金风险发现**：附代码或配置证据并按影响排序。
5. **失败恢复与对账方案**。
6. **可执行验证矩阵**。
7. **仍未证明的事项**。

不要把“接口返回成功”写成“资金流程正确”，除非订单状态、副作用次数和对账路径都得到证据支持。
