# 中国开发环境诊断

网络安装故障常被一句“换国内源”草率处理，但真正原因可能位于 DNS、代理、企业证书、工具配置优先级、守护进程或依赖自身。本 Skill 先定位层级，再给出可撤销修复。

## 边界

处理开发机和 CI 中的依赖获取、源码拉取、容器镜像拉取与代理证书问题。业务 API 故障、数据库性能和应用代码异常不在范围内。

未经授权，不修改系统级网络、企业安全软件、全局证书库或共享 CI 配置。

Docker 场景按需读取 [`references/docker-proxy-official.md`](references/docker-proxy-official.md)，并先区分 CLI、daemon、Desktop 与构建容器。

## 工作流

### 1. 保存原始证据

记录完整命令、首次关键错误、发生时间、工具与运行时版本、操作系统、网络位置、是否使用 VPN 或企业代理，以及同机已知正常的对照请求。脱敏令牌、账号、代理密码和内部域名。

不要先清缓存，因为它会删除可用于比较的证据。

### 2. 判断失败层级

按顺序区分：

- DNS 解析；
- TCP 连接与防火墙；
- HTTP 代理或 PAC；
- TLS 握手、系统时间和证书链；
- Registry、仓库或镜像鉴权；
- 包管理器配置与锁文件；
- 安装脚本、原生二进制、架构或编译工具链。

只修复证据指向的层级，不一次改五项配置。

### 3. 读取配置优先级

列出环境变量、项目级配置、用户级配置、系统级配置和工具默认值，标明最终生效值与来源。重点检查重复的 proxy、registry、CA、证书路径、no_proxy 和大小写环境变量。

输出时隐藏 URL 中的用户名、密码和访问令牌。

### 4. 区分客户端与守护进程

Docker CLI、Docker daemon、桌面应用和构建容器可能使用不同代理配置。`curl` 能访问不代表 daemon 能拉镜像；终端能安装也不代表 CI 或 IDE 子进程继承了相同环境。

为每个执行主体单独记录网络出口和配置来源。

### 5. 正确处理企业证书

若证据显示 TLS 被企业代理重新签发，应通过组织认可的 CA 分发方式让目标工具信任正确证书，并验证证书链和主机名。

拒绝把关闭 TLS 校验、`strict-ssl=false`、忽略证书错误或使用明文 HTTP 当作正式修复。这些设置如果已存在，应标记风险并给出恢复方式。

### 6. 谨慎试验镜像源

镜像只能作为范围明确、可撤销的对照实验。使用前确认维护者、同步延迟、包完整性、目标生态与组织政策；保留原配置并记录回滚命令。

锁文件中的下载地址、二进制 postinstall 和 Git 依赖可能绕过 registry，换源后仍需验证所有实际下载主机。

### 7. 检查缓存、锁文件和架构

只有证据指向损坏缓存时才清理相应条目。检查锁文件版本、包管理器版本、离线存储、Node/Python/Rust 版本、CPU 架构和原生构建依赖。

优先做只读检查或复制到临时目录复现，不删除整个全局缓存或项目锁文件。

### 8. 做单变量验证

每次只改变一个因素，重新运行最小命令，记录耗时、状态码、实际连接端点和错误变化。修复后同时验证安装、锁文件稳定性、校验和或签名，以及原配置能否恢复。

### 9. 输出根因与长期方案

区分已证明根因、较强推断和未知。给出临时绕行、正式修复、风险、回滚和需要网络或安全团队处理的证据包。

## 停止条件

- 需要代理密码、私有仓库令牌或企业根证书但用户未提供安全渠道；
- 必须修改系统或共享基础设施且未获授权；
- 证据显示被组织安全策略明确拦截；
- 唯一下一步是关闭 TLS、绕过鉴权或使用来源不明镜像；
- 故障实际属于业务服务或应用逻辑。

## 输出约定

1. **诊断结论**：已定位、最可能、信息不足或范围外。
2. **分层证据表**：DNS、连接、代理、TLS、鉴权、工具与依赖。
3. **生效配置与来源**：必须脱敏。
4. **最小修复步骤与验证命令**。
5. **镜像或代理变更的风险与回滚**。
6. **长期治理建议**。
7. **仍需网络、平台或安全团队确认的事项**。

“换源后能装”只是现象，除非同时解释原始失败和供应链风险，否则不是完整结论。
